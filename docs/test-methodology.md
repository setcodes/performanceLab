# Методика нагрузочного исследования

## Проверяемые гипотезы

Исследование не должно заканчиваться одной цифрой «максимум слоёв». Базовые
гипотезы формулируются отдельно:

1. **H-FEATURES:** при фиксированных 10 слоях и одном source рост видимых объектов
   определяет предел главного потока и памяти.
2. **H-VERTICES:** при фиксированном количестве объектов время кадра зависит от
   суммарного числа видимых вершин сильнее, чем от числа features.
3. **H-LAYERS:** при фиксированной геометрии рост style layers увеличивает CPU/GPU
   стоимость даже без роста сетевого трафика.
   Проверять в двух вариантах: общий набор во всех слоях и N уникальных объектов
   в каждом слое. Эти варианты измеряют разные причины деградации.
4. **H-SOURCES:** дублирование sources дороже дублирования layers из-за отдельных
   worker/source lifecycle и повторной обработки данных.
5. **H-DELIVERY:** MVT удерживает браузерные метрики в допустимом диапазоне при
   общем датасете, при котором цельный GeoJSON уже неприемлем.
6. **H-SERVER:** Martin/PostGIS обеспечивает заданный p95 и процент ошибок при
   целевой конкурентной нагрузке после прогрева.

## Рекомендуемая матрица

| Ось | Значения первого прохода |
|---|---|
| Точки | 10k, 50k, 100k, 250k |
| Линии | 1k, 10k, 50k × 8/32/128 вершин |
| Полигоны | 1k, 5k, 10k × 16/64/256 вершин |
| Style layers | 1, 10, 25, 50, 100, 200 |
| Sources | 1, 2, 5, 10 |
| Collision proxy | выключен / включён |
| DPR | 1 / 2 |
| Доставка | GeoJSON / MVT |
| Набор геометрий | один тип / точки + линии / все три типа |
| Подложка | выключена для baseline / OSM только для ручной UX-проверки |
| Кеш | холодный / прогретый |
| Нагрузка Martin | 25, 75, 150, 300+ RPS |

Начинать нужно не с полного декартова произведения, а с one-factor-at-a-time.
После нахождения перелома провести небольшую факторную матрицу вокруг него.

## Ключевые показатели

Клиент:

- frame time p50/p95/p99 — основная метрика плавности;
- FPS — удобный, но вторичный агрегат;
- кадры >16,7/50/100 мс;
- long tasks и их суммарная длительность;
- first render и idle;
- JS heap после серии одинаковых прогонов;
- переданные и декодированные байты;
- WebGL renderer, DPR и viewport.

Сервер:

- achieved RPS, а не только заданный arrival rate;
- http_req_duration p50/p95/p99;
- доля HTTP/прикладных ошибок;
- размер тайлов по source и zoom;
- CPU/RAM Martin и PostGIS (`docker stats` или внешняя телеметрия);
- число соединений и медленные SQL-запросы PostGIS.

## Ограничения версии 0.1

- collision proxy измеряет placement значков, но не полную стоимость текстовых
  glyphs; шрифтовой corpus следует добавить отдельной задачей;
- Performance Memory API доступен не во всех браузерах;
- `transferSize` может быть нулём для кешированных ресурсов;
- UI не измеряет потребление GPU memory, так как WebGL не предоставляет
  переносимого стандартизованного API;
- MapServer подключён как ручной профиль, но WMS-матрица ещё не автоматизирована;
- OSM не участвует в автоматическом pan/zoom: публичный tile-сервис запрещает
  headless-префетч, а его сетевые задержки не относятся к MapLibre baseline;
- браузерные результаты между разным оборудованием нельзя объединять в один
  рейтинг без сегментации.

## Формат вывода для технологического решения

Итог должен содержать не «MapLibre выдерживает N слоёв», а границы применимости:

```text
На профиле оборудования X, Chromium Y, DPR 1, viewport 1440×900:
- до A видимых точек при 10 простых layers: frame p95 = B мс;
- при C vertices и 50 layers начинается деградация выше 33 мс;
- MVT сохраняет p95 ниже D мс при общем датасете E;
- Martin обеспечивает F RPS с p95 G мс и ошибками H%;
- для более тяжёлых сценариев обязательны clustering/generalization/LOD.
```
