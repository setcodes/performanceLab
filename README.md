# MapLibre Performance Lab

Воспроизводимый стенд для проверки производительности чистого MapLibre GL JS и
нагрузочной способности цепочки `MapLibre → Martin → PostGIS`. Это baseline-PoC:
он не содержит корпоративный Map SDK и не изменяет проект ЦП ЕИТП.

## Что измеряет стенд

Браузерный контур независимо изменяет:

- количество GeoJSON-объектов или объём MVT-датасета;
- один или несколько одновременно отображаемых типов геометрии;
- число вершин на объект;
- общее количество MapLibre sources, распределённых между выбранными типами;
- количество style layers;
- стоимость placement/collision через специальный icon-proxy слой;
- DPR, viewport, браузер и оборудование.

Результат содержит FPS, p50/p95/p99 времени кадра, кадры дольше 16,7 и 50 мс,
время генерации данных, setup/first render/idle, long tasks, сеть, JS heap и
WebGL renderer.

Серверный контур k6 отдельно измеряет RPS, p95/p99, ошибки и размер MVT-ответов.
Разделение обязательно: один браузер не является генератором серверной нагрузки,
а k6 не измеряет WebGL и главный поток браузера.

## Быстрый старт: только браузер и GeoJSON

Требования: Node.js 22.12+.

```bash
npm install
npm run dev
```

Откройте <http://localhost:4173>. Для автоматической матрицы:

```bash
npx playwright install chromium
npm run test:browser
npm run report
```

Интерфейс разделён на настройки слева, карту по центру и статистику справа.
Панель статистики сворачивается кнопкой в заголовке; её состояние и все значения
формы сохраняются в `localStorage`. Кнопка «Сбросить настройки» возвращает
исходную конфигурацию и удаляет сохранённые значения.

## Весь стенд одной командой

Требуется только Docker с поддержкой Compose (Docker Desktop, OrbStack или
совместимый Docker Engine). Node.js и локально установленный PostgreSQL не нужны.

```bash
git clone https://github.com/setcodes/performanceLab.git
cd performanceLab
docker compose up -d --wait
```

После запуска откройте <http://localhost:4173>. В контейнерах автоматически
поднимаются:

- production-сборка интерфейса с reverse proxy `/tiles`;
- Martin на <http://localhost:3000>;
- PostgreSQL 17 с PostGIS 3.5;
- детерминированные тестовые данные и профили разброса 3, 30 и 150 км.

Готовые multi-arch образы публикуются в GitHub Container Registry:

- `ghcr.io/setcodes/performancelab-web:latest`;
- `ghcr.io/setcodes/performancelab-martin:1.3.1`;
- `ghcr.io/setcodes/performancelab-postgis:17-3.5`.

Обычный запуск не собирает приложение и не загружает базовые Node/nginx-слои
по отдельности. Для принудительной локальной пересборки после изменения исходников:

```bash
docker compose up -d --build --wait
```

Первый запуск дольше последующих: PostGIS выполняет SQL из
`infra/postgis/init/` и создаёт 250 000 точек, 50 000 линий и 10 000 полигонов
для основной выборки и каждого из трёх профилей разброса. Данные сохраняются в
именованном Docker volume и повторно не генерируются при обычном перезапуске.

Управление стендом:

```bash
docker compose ps
docker compose logs -f web martin postgis
docker compose down
```

Порт интерфейса можно изменить:

```bash
WEB_PORT=8088 docker compose up -d --wait
```

Полностью пересоздать БД и повторить начальное заполнение:

```bash
docker compose down -v
docker compose up -d --wait
```

Команда с `-v` удаляет только volume этого compose-проекта и все находящиеся в
нём тестовые данные.

В публикации через Codex Sites режим GeoJSON работает автономно. Для MVT нужен
отдельно опубликованный Martin/PostGIS; его адрес передаётся на этапе сборки
через `VITE_MVT_BASE_URL`.

Поле «DPR рендера» управляет `pixelRatio` MapLibre в диапазоне 0.5–4. Оно
меняет физический размер WebGL-буфера и позволяет сравнивать нагрузку GPU при
разной плотности пикселей, не изменяя системный DPR браузера.

«Разброс» выбирает один из одинаковых пространственных профилей для GeoJSON и
MVT: 3, 30 или 150 км вокруг центра Москвы. Малый радиус создаёт плотный кластер,
большой распределяет тот же объём данных по региону. MVT-профили хранятся в
отдельных таблицах PostGIS.

После обновления уже существующего Docker volume один раз примените профили:

```bash
npm run infra:profiles
```

Каждый Benchmark получает **Performance score от 0 до 1000**: до 550 очков за
плавность, 250 за скорость подготовки сцены и idle, 200 за стабильность. Кнопка
«Скоринг» открывает рейтинг до 30 сохранённых запусков. В одно сравнение попадают
только одинаковые настройки; способ доставки GeoJSON/MVT может отличаться.

### Режимы стенда

В режиме **Benchmark** выполняется фиксированный сценарий pan/zoom и формируется
воспроизводимый результат. Его можно посмотреть в структурированном диалоге,
скачать как JSON для автоматической обработки или как автономный HTML-отчёт.

В режиме **Realtime** сцена остаётся интерактивной, а правая панель обновляется
раз в секунду. Она показывает rolling FPS, frame p95, long tasks, JS heap,
сетевой объём, текущие sources/layers, размер canvas, zoom, количество уникальных
видимых объектов и суммарное число попаданий объектов в style layers. Быстрые
кнопки позволяют добавлять и убирать объекты, sources и layers, а также менять
сложность стиля с немедленным перестроением сцены.

Web API браузера не предоставляет достоверный общий процент загрузки CPU и GPU.
Поэтому клиентский realtime-монитор использует FPS, время кадра, long tasks и
JS heap как индикаторы нагрузки. Серверные CPU/RAM и нагрузку PostgreSQL следует
собирать отдельным мониторингом одновременно с тестом.

В ручном интерфейсе доступна растровая подложка OpenStreetMap. Она включена по
умолчанию, отображает обязательную атрибуцию и запрашивает только тайлы текущего
viewport. Автоматические performance-тесты запускаются с `?basemap=none`: политика
OSM запрещает headless pan/zoom, а внешняя сеть сделала бы baseline невоспроизводимым.

Чекбоксы «Точки», «Линии» и «Полигоны» независимы. Поле «Объектов на тип»
применяется к каждому выбранному типу: например, 5 000 и три чекбокса создают
15 000 GeoJSON features. Поле «Источники всего» задаёт итоговое число тематических
sources; при трёх типах его минимум равен трём. `layerCount` остаётся общим числом
style layers.

### Профили ГОСТ Р 70107-2022

Селектор профиля подготавливает три предметных сценария. Они не копируют знаки
стандарта пиксель в пиксель, но создают сопоставимую работу для MapLibre: составные
линии и обводки, пунктиры, повторяющиеся стрелки, sprite-иконки, подписи с halo,
collision/placement и штрихованные полигоны.

- **ГОСТ · оптимизированный** — 3 тематических sources и 30 style layers;
- **ГОСТ · рабочий** — 4 тематических sources и 48 style layers;
- **ГОСТ · слои буквально** — 59 тематических sources и 84 style layers.

Подложка OSM считается отдельно и при включении добавляет ещё один source и один
raster style layer. Профили не переключают способ доставки автоматически: один и
тот же состав можно сравнить в GeoJSON и MVT. В режиме MVT каждый отдельный source
создаёт собственный поток запросов тайлов, поэтому вариант 59/84 предназначен как
заведомо тяжёлая граница, а не как рекомендуемая архитектура.

Поле «Распределение объектов по слоям» поддерживает два разных эксперимента:

- **Общий набор во всех слоях** — каждый style layer повторно отображает один и
  тот же набор. Это проверяет стоимость layers и overdraw при постоянном объёме данных.
- **Уникальный набор для каждого слоя** — каждый слой получает отдельную группу
  размером «Объектов в слое». Например, 100 слоёв × 1 000 объектов создают
  суммарную нагрузку 100 000 features.

В GeoJSON группы создаются генератором и разделяются по `layerBucket`. В MVT
слои получают непересекающиеся диапазоны через фильтр по `id`. Для MVT в PostGIS
должно находиться не меньше `слои × объекты в слое` объектов выбранного типа;
иначе последние слои закономерно получат меньше данных.

Отчёт создаётся в `results/reports/index.html`, сырые результаты — в
`results/raw/`.

## Полный MVT-контур для разработки и тестов

Для запуска интерфейса через локальный Vite и выполнения тестовой матрицы
требуются Node.js 22.12+ и Docker Compose.

```bash
npm run infra:up
curl http://localhost:3000/catalog
npm run test:browser:mvt
npm run load:smoke
npm run load
npm run report
```

Первый запуск создаёт детерминированные наборы:

- 250 000 точек;
- 50 000 линий по 16 вершин;
- 10 000 полигонов примерно по 16 вершин.

Для другого объёма пересоздайте данные без удаления Docker volume:

```bash
POINT_COUNT=1000000 LINE_COUNT=200000 POLYGON_COUNT=50000 VERTICES=32 npm run infra:seed
```

После reseed перезапустите Martin, чтобы каталог и bounds гарантированно
соответствовали новым данным:

```bash
docker compose restart martin
```

Удаление контейнеров с сохранением БД: `npm run infra:down`. Полное удаление
тестовой БД и volume: `npm run infra:reset`.

## Нагрузочные профили

- `smoke`: 2 VU, 20 секунд;
- `load`: рост от 10 до 150 запросов тайлов в секунду;
- `stress`: рост до 800 запросов в секунду, запускается командой ниже.

```bash
K6_PROFILE=stress docker compose --profile load run --rm k6 run /tests/martin.js
```

Пороговые значения можно передать окружением:

```bash
MAX_P95_MS=300 MAX_ERROR_RATE=0.005 npm run load
```

Браузерные performance budgets по умолчанию только записываются и не валят тест
на неизвестном оборудовании. После калибровки эталонной машины их можно включить:

```bash
ENFORCE_BUDGETS=1 FRAME_P95_BUDGET_MS=33 npm run test:browser
```

## MapServer: второй профиль

MapServer не участвует в основном MVT baseline и включается отдельно:

```bash
npm run mapserver:up
```

WMS GetCapabilities:

```text
http://localhost:8080/?map=/etc/mapserver/benchmark.map&SERVICE=WMS&REQUEST=GetCapabilities
```

Профиль нужен для будущего сравнения WMS/растрового рендеринга; браузерная
матрица первой версии пока автоматизирует GeoJSON и MVT.

## Методика корректного эксперимента

1. Зафиксировать ОС, CPU, RAM, GPU, браузер, viewport и DPR.
2. Закрыть фоновые приложения и прогреть браузер одним холостым запуском.
3. Для каждого сценария сделать минимум 5 повторов; сравнивать медиану и худший p95.
4. Холодный серверный тест выполнять после перезапуска Martin/PostGIS, прогретый —
   повторно без перезапуска.
5. Не менять одновременно объекты, вершины, layers и sources: увеличивать одну
   ось, остальные держать постоянными.
6. Не запускать k6 на том же слабом ПК, производительность которого измеряется,
   при финальном серверном испытании.
7. Сохранять commit SHA, параметры seed и результат вместе.

Предлагаемый критерий для типового рабочего места: интерактивный сценарий
считается приемлемым при frame p95 ≤ 33 мс, отсутствии кадров > 100 мс во время
обычного pan/zoom и отсутствии роста JS heap между пятью одинаковыми прогонами.
Это стартовая гипотеза, а не готовый норматив ЦП ЕИТП.

## Структура

```text
src/                    UI, сценарии, Web Worker и браузерные метрики
tests/browser/          автоматическая Playwright-матрица
tests/load/             k6-нагрузка на Martin
infra/postgis/init/     схема и детерминированный генератор больших данных
infra/mapserver/        дополнительный WMS-профиль
scripts/                reseed и сбор автономного HTML-отчёта
results/raw/            JSON отдельных прогонов
results/reports/        сводный HTML
```

Подробные сценарии и правила интерпретации: [docs/test-methodology.md](docs/test-methodology.md).
